# 01_bad_prompts_board_service 코드 리뷰

## 1. 리뷰 대상
- 프롬프트 방식: 01_bad_prompts_board_service
- 리뷰 기준: 동일 기능에 대한 구현 결과 비교
- 리뷰 원칙: 실제 코드 기반, 추측 금지

## 2. 실험 맥락
### 실험 조건
- 같은 초기 저장소 상태
- 같은 AI 툴
- 같은 모델
- 시간 제한: 20~30분

### 실험 목적
동일한 기능을 서로 다른 프롬프트 전략으로 개발했을 때  
구조, 품질, 테스트, 유지보수성이 어떻게 달라지는지 비교하기 위함.

### 통제 환경
- H2 Database
- 단순 HTML/CSS/JS

## 3. 구현 요약
### 전체 인상
- Spring Boot 기반 백엔드와 정적 HTML 4개로 게시판 CRUD를 빠르게 완성한 형태다.
- 백엔드는 `post` 패키지 아래에 계층을 나눴지만, 권한과 예외 정책은 단순하다.
- 테스트는 도메인, 서비스, 컨트롤러까지 작성됐지만 저장소와 실제 UI 흐름은 다루지 않는다.
- 인증 모델은 없고, 수정·삭제 권한은 작성자 이름 문자열 비교에 의존한다.
- 프레임워크 기본 설정을 많이 사용해 실행은 가능하지만 동작 일관성 리스크가 남아 있다.

### 확인된 주요 구현 범위
- 게시글 생성, 목록 조회, 상세 조회, 수정, 삭제 API 구현
- `Post` 엔티티와 `JpaRepository` 기반 저장소 구현
- 요청 DTO 검증과 검증 실패 응답 처리 구현
- 정적 HTML 기반 목록, 등록, 상세, 수정 화면 구현
- 수정·삭제 시 `X-Author-Name` 헤더를 사용하는 작성자 확인 로직 구현
- 도메인 테스트, 서비스 단위 테스트, 컨트롤러 WebMvc 테스트 작성

## 4. 평가 기준별 리뷰

### 4.1 빌드 성공
- 빌드 가능 여부
- 실패 시 원인
- 관련 근거 파일 또는 설정

평가: 성공
근거: `build.gradle`에 Spring Boot, JPA, Security, Validation, H2 의존성이 선언돼 있다. `gradlew.bat test`와 `gradlew.bat bootJar`를 실제 실행했을 때 성공했다.
리스크: 최초 실행 시 Gradle Wrapper와 의존성 다운로드가 필요하다. 네트워크가 없으면 초기 빌드가 막힌다.

### 4.2 실행 가능
- 애플리케이션 실행 가능 여부
- 실행에 필요한 조건
- 실행 막는 요소

평가: 실행 가능
근거: `BoardPromptApplication` 메인 클래스가 존재하고, 생성된 `build/libs/boardPrompt-0.0.1-SNAPSHOT.jar`를 실제 실행했을 때 애플리케이션 시작 로그와 Tomcat 기동 로그가 확인됐다. H2는 메모리 DB로 자동 기동된다.
리스크: `SecurityConfig`에서 `/api/**`만 허용하고 그 외 요청은 인증을 요구한다. 정적 HTML 화면은 기본 생성 계정으로 로그인해야 접근 가능하며, 별도 사용자 설정은 코드상 없다.

### 4.3 테스트 개수
- 테스트 파일 수
- 테스트 케이스 수
- 테스트 범위

평가: 테스트 파일 4개, 테스트 케이스 22개
근거: `BoardPromptApplicationTests`, `PostTest`, `PostServiceTest`, `PostControllerTest`가 존재한다. `@Test`는 총 22개다. 범위는 컨텍스트 로드, 도메인 메서드, 서비스 CRUD, 컨트롤러 CRUD 응답까지다.
리스크: 저장소 통합 테스트와 브라우저 수준 테스트는 없다.

### 4.4 테스트 품질
- 정상 흐름만 검증하는지
- 실패/예외/경계값을 다루는지
- 테스트가 구조를 보호하는 수준인지

평가: 보통
근거: `PostServiceTest`는 수정·삭제의 성공, 미존재, 권한 오류를 검증한다. `PostControllerTest`는 CRUD의 정상 흐름과 일부 404를 검증한다. 그러나 요청 검증 실패, 403 응답, 정적 페이지 접근, 보안 설정 실제 동작은 테스트하지 않는다.
리스크: 현재 테스트만으로는 검증 응답 포맷, Security 설정, JPA 매핑, 실제 DB 연동 문제를 막기 어렵다.

### 4.5 패키지 구조
- 계층 분리 상태
- 역할 분리 명확성
- 파일 배치 일관성
- 확장 가능성

평가: 보통
근거: `post.domain`, `post.application`, `post.infrastructure`, `post.presentation`으로 계층이 나뉘어 있다. `global.security`, `global.exception`도 별도 패키지로 분리돼 있다. 다만 게시글 관련 로직은 단일 서비스와 단일 컨트롤러에 집중돼 있고, 프런트엔드는 HTML 파일마다 CSS와 JS가 인라인으로 들어 있다.
리스크: 기능이 늘어나면 서비스 비대화와 화면 스크립트 중복이 빠르게 커질 수 있다.

### 4.6 권한 처리
- 인증/인가 관련 처리 존재 여부
- 보호 범위
- 우회 가능성
- 하드코딩 여부

평가: 미흡
근거: `SecurityConfig`는 `/api/**` 전체를 `permitAll()`로 열어 둔다. 수정·삭제 권한은 `PostService`에서 저장된 `authorName`과 요청 헤더 `X-Author-Name` 문자열이 같은지만 비교한다. 프런트엔드는 `localStorage`의 `currentAuthorName` 값을 그대로 헤더로 보낸다.
리스크: 헤더 값만 바꾸면 권한을 우회할 수 있다. UI 접근과 API 보호 범위도 일치하지 않는다.

### 4.7 예외 처리
- 예외 처리 방식
- 공통 예외 처리 존재 여부
- 사용자 응답 일관성
- 누락된 영역

평가: 미흡
근거: `GlobalExceptionHandler`는 `MethodArgumentNotValidException`만 공통 처리한다. `ForbiddenException`은 `PostController`의 수정·삭제 메서드에서 각각 직접 처리한다. 조회 실패는 빈 404 응답이고, 기타 런타임 예외나 DB 예외에 대한 공통 응답은 없다.
리스크: 엔드포인트마다 응답 형식이 달라지고, 예외가 늘어날수록 컨트롤러 중복이 증가한다.

### 4.8 코드 중복
- 반복되는 로직 존재 여부
- 중복된 DTO/검증/응답/쿼리/핸들러 여부
- 리팩토링 필요 수준

평가: 미흡
근거: `CreatePostRequest`와 `UpdatePostRequest`는 필드와 검증 규칙이 동일하다. `create-post.html`과 `post-edit.html`은 입력 검증, 에러 표시, 메시지 처리 코드가 거의 같은 구조다. `PostController`의 수정·삭제는 `ForbiddenException` 처리 로직도 중복된다.
리스크: 규칙 변경 시 수정 지점이 여러 곳으로 늘어난다. 프런트와 백엔드 규칙 불일치도 생기기 쉽다.

## 5. 구조적 장점
- `post` 패키지를 도메인, 애플리케이션, 인프라, 프레젠테이션으로 나눠 기본 계층 구조를 갖췄다.
- 요청 DTO에 Bean Validation을 적용하고 `GlobalExceptionHandler`로 검증 실패 응답을 한곳에서 정리한다.
- `PostServiceTest`가 수정·삭제의 권한 실패와 미존재 케이스를 포함해 핵심 분기 일부를 보호한다.
- 정적 화면이 목록, 등록, 상세, 수정으로 분리돼 사용 흐름을 코드상 바로 따라갈 수 있다.
- H2 메모리 DB와 JPA 자동 스키마 생성으로 로컬 실행 준비가 단순하다.

## 6. 구조적 한계
- API 전체가 인증 없이 열려 있고, 수정·삭제 권한도 작성자 이름 문자열 비교만 사용한다.
- 정적 화면은 인증이 필요하지만 API는 공개라서 보안 정책이 일관되지 않다.
- 예외 응답 형식이 검증 실패, 권한 실패, 404에서 서로 다르다.
- 생성/수정 DTO가 분리돼 있지만 실제 내용은 중복이다.
- 등록 화면과 수정 화면의 JS 검증 로직이 거의 복제돼 있다.
- 컨트롤러 테스트는 서비스 Mock 기반이라 Security 실제 필터 동작과 DB 연동을 보호하지 못한다.
- `application.properties`에 명시 설정이 거의 없어 보안, JPA, H2 동작이 프레임워크 기본값에 의존한다.

## 7. 유지보수성 관점 총평
아래 4개 항목으로 정리한다.

- 변경 용이성: 백엔드 계층 분리가 있어 작은 수정은 가능하다. 하지만 검증 규칙과 권한 처리가 DTO, 서비스, HTML 스크립트에 흩어져 있어 규칙 변경 비용이 커진다.
- 기능 확장 용이성: 현재 범위의 CRUD 확장은 가능하다. 다만 단일 서비스 구조와 인라인 프런트 스크립트는 검색, 페이징, 사용자 모델 추가 시 빠르게 부담이 된다.
- 버그 발생 가능성: 권한 우회 가능성이 크고 응답 형식도 일관되지 않다. 프런트와 백엔드 검증 중복 때문에 동작 차이 버그가 생기기 쉽다.
- 리팩토링 필요도: 높다. 권한 모델, 예외 처리, DTO 중복, 프런트 스크립트 분리가 우선 정리 대상이다.
