# 03.Role-high_Structured 코드 리뷰

## 1. 리뷰 대상
- 프롬프트 방식: 03.Role-high_Structured
- 리뷰 기준: 동일 기능에 대한 구현 결과 비교
- 리뷰 원칙: 실제 코드 기반, 추측 금지

## 2. 실험 맥락
### 실험 조건
- 같은 초기 저장소 상태
- 같은 AI 툴
- 같은 모델
- 시간 제한: 20~30분

### 실험 목적
동일한 기능을 서로 다른 프롬프트 전략으로 개발했을 때  
구조, 품질, 테스트, 유지보수성이 어떻게 달라지는지 비교하기 위함.

### 통제 환경
- H2 Database
- 단순 HTML/CSS/JS

## 3. 구현 요약
### 전체 인상
- `post` 기능은 `presentation`, `application`, `domain`, `infrastructure`로 분리되어 있다.
- CRUD API와 정적 HTML/JS 화면은 모두 구현되어 있다.
- 테스트는 서비스와 컨트롤러까지 작성되어 있지만, 보안과 실제 저장소 연동은 검증하지 않는다.
- 권한과 예외 처리는 구조만 일부 준비되어 있고 구현은 얕다.
- 프롬프트에서 요구한 구조는 반영했지만, 공통 규약과 완성도는 덜 채워진 상태다.

### 확인된 주요 구현 범위
- 게시글 생성, 목록 조회, 단건 조회, 수정, 삭제 API 구현: `src/main/java/com/example/boardPrompt/post/presentation/PostController.java`
- 게시글 서비스 계층 4개 분리 구현: `src/main/java/com/example/boardPrompt/post/application`
- `PostRepositoryPort`와 `PostRepositoryAdapter`를 사용한 저장소 추상화 구현: `src/main/java/com/example/boardPrompt/post/application/port/PostRepositoryPort.java`, `src/main/java/com/example/boardPrompt/post/infrastructure/PostRepositoryAdapter.java`
- JPA 엔티티와 Spring Data JPA 저장소 구현: `src/main/java/com/example/boardPrompt/post/infrastructure/PostJpaEntity.java`, `src/main/java/com/example/boardPrompt/post/infrastructure/PostJpaRepository.java`
- 정적 화면 4개와 JS 파일 4개 구현: `src/main/resources/static`
- 서버 요청 DTO 검증 구현: `src/main/java/com/example/boardPrompt/post/presentation/dto/PostCreateRequest.java`
- Spring Security 설정 파일 존재: `src/main/java/com/example/boardPrompt/global/config/SecurityConfig.java`
- 서비스 테스트, 컨트롤러 테스트, 컨텍스트 로드 테스트 구현: `src/test/java`

## 4. 평가 기준별 리뷰

### 4.1 빌드 성공
- 빌드 가능 여부
- 실패 시 원인
- 관련 근거 파일 또는 설정

평가:
빌드는 성공한다. 2026-03-11에 `gradlew.bat build`가 `BUILD SUCCESSFUL`로 종료되었고 JAR가 생성됐다.

근거:
`build.gradle`에 Spring Boot, JPA, Security, Validation, H2 의존성이 선언되어 있다. `build/libs/boardPrompt-0.0.1-SNAPSHOT.jar`와 `build/libs/boardPrompt-0.0.1-SNAPSHOT-plain.jar`가 생성됐다.

리스크:
`PostControllerTest`의 `@MockBean` 사용으로 deprecation warning 4건이 발생했다. 현재 빌드는 통과하지만 테스트 코드 유지보수 비용은 늘어날 수 있다.

### 4.2 실행 가능
- 애플리케이션 실행 가능 여부
- 실행에 필요한 조건
- 실행 막는 요소

평가:
애플리케이션은 실행된다. 다만 익명 사용자가 정적 화면에 바로 접근하는 흐름은 막혀 있다.

근거:
2026-03-11에 `gradlew.bat bootRun`으로 Tomcat 8080 기동을 확인했다. 같은 실행에서 `GET /api/posts`는 200을 반환했고, `GET /post-list.html`은 403을 반환했다. `SecurityConfig.java:17-22`는 `/api/**`만 허용하고 나머지 요청은 인증을 요구한다.

리스크:
실험 조건이 단순 HTML/CSS/JS인데 정적 페이지가 인증 없이 열리지 않는다. 백엔드는 기동되지만 기본 UI 흐름은 바로 사용하기 어렵다.

### 4.3 테스트 개수
- 테스트 파일 수
- 테스트 케이스 수
- 테스트 범위

평가:
테스트 파일은 6개이고 테스트 케이스는 18개다. 범위는 서비스 단위 테스트와 컨트롤러 웹 테스트에 집중되어 있다.

근거:
`src/test/java` 아래 파일은 `BoardPromptApplicationTests`, `PostCreateServiceTest`, `PostDeleteServiceTest`, `PostFindServiceTest`, `PostUpdateServiceTest`, `PostControllerTest` 총 6개다. `@Test`는 총 18개다. 서비스 계층 8개, 컨트롤러 9개, 컨텍스트 로드 1개로 구성된다.

리스크:
리포지토리, JPA 매핑, 보안 설정, 정적 JS 동작을 검증하는 테스트는 없다. 실제 런타임 문제를 막는 범위는 제한적이다.

### 4.4 테스트 품질
- 정상 흐름만 검증하는지
- 실패/예외/경계값을 다루는지
- 테스트가 구조를 보호하는 수준인지

평가:
기본 성공 흐름과 일부 실패 흐름은 검증한다. 구조 보호 수준은 보통 이하이다.

근거:
`PostControllerTest.java`는 생성 201, 조회 200, 없는 ID 404, 수정 404, 삭제 404, 제목 누락 400을 검증한다. `PostFindServiceTest.java`, `PostUpdateServiceTest.java`, `PostDeleteServiceTest.java`는 없는 ID 처리도 확인한다. 그러나 `PostControllerTest.java:28-29`는 `@AutoConfigureMockMvc(addFilters = false)`를 사용해 실제 보안 필터를 끈다. 제목 길이 500자 초과, 내용 누락, 저장소 실패, 예외 응답 형식은 테스트하지 않는다.

리스크:
실행 시 드러난 보안 설정 문제를 테스트가 잡지 못한다. 테스트가 계층 간 계약과 런타임 설정을 충분히 보호하지 못한다.

### 4.5 패키지 구조
- 계층 분리 상태
- 역할 분리 명확성
- 파일 배치 일관성
- 확장 가능성

평가:
패키지 구조는 비교적 명확하다. 다만 실제 구현 밀도는 `post`에 치우쳐 있다.

근거:
`docs/03.Role-high_Structured.md`의 구조 요구대로 `post/presentation`, `post/application`, `post/domain`, `post/infrastructure`가 구성되어 있다. `PostRepositoryPort.java`와 `PostRepositoryAdapter.java`로 저장소 의존성을 분리했다. 반면 `auth/application`, `auth/domain`, `auth/infrastructure`, `auth/presentation`, `global/exception`, `global/security`는 `.gitkeep`만 있고 실제 클래스가 없다.

리스크:
구조 틀은 있지만 공통 영역이 비어 있다. 기능이 늘어나면 현재 구조를 그대로 확장하기보다 다시 채워 넣는 작업이 필요하다.

### 4.6 권한 처리
- 인증/인가 관련 처리 존재 여부
- 보호 범위
- 우회 가능성
- 하드코딩 여부

평가:
권한 처리는 미흡하다.

근거:
`SecurityConfig.java:20-22`는 `/api/**` 전체를 `permitAll()`로 열어 둔다. 같은 설정은 그 외 요청에 인증을 요구한다. 실제 인증/인가 로직은 `auth` 패키지에 구현되어 있지 않고 `.gitkeep`만 있다. 실행 확인에서도 `/post-list.html`은 403이고 `/api/posts`는 200이었다.

리스크:
API는 모두 무인증으로 열려 있고, 정적 UI는 막혀 있다. 보호 범위가 기능 목적과 맞지 않고 역할 기반 제어도 없다.

### 4.7 예외 처리
- 예외 처리 방식
- 공통 예외 처리 존재 여부
- 사용자 응답 일관성
- 누락된 영역

평가:
예외 처리는 부분 구현 수준이다.

근거:
코드 전체에서 `@ControllerAdvice`나 `@ExceptionHandler`는 확인되지 않았다. `PostController.java`는 없는 ID를 `ResponseEntity.notFound().build()`로 직접 반환한다. 입력 검증은 `PostCreateRequest.java:12-17`의 `@Valid`에 의존한다. `post-create.js:90`, `post-edit.js:121`은 실패 응답에서 `data.message`를 기대하지만, 서버 쪽 공통 메시지 포맷은 정의되어 있지 않다.

리스크:
400, 404, 기타 실패 응답의 형식이 일관되지 않다. 프런트가 서버 오류를 세밀하게 표시하기 어렵고, 예외 처리 규약을 기능별로 다시 작성할 가능성이 높다.

### 4.8 코드 중복
- 반복되는 로직 존재 여부
- 중복된 DTO/검증/응답/쿼리/핸들러 여부
- 리팩토링 필요 수준

평가:
중복은 눈에 띄는 편이다.

근거:
`post-create.js`와 `post-edit.js`에는 `showMessage`, `clearMessage`, `clearFieldErrors`, `setFieldError`, `validate`가 거의 같은 형태로 반복된다. `PostController.java`도 조회와 수정에서 `Optional`을 `404`로 변환하는 패턴이 반복된다. 서비스 4개는 역할은 분리됐지만 대부분 단일 저장소 호출 위임이다.

리스크:
입력 검증 규칙이나 메시지 형식을 바꾸면 여러 JS 파일을 같이 수정해야 한다. 기능이 늘수록 중복이 빠르게 누적될 구조다.

## 5. 구조적 장점
- `post` 패키지가 계층별로 분리되어 있어 파일 탐색과 책임 구분이 명확하다.
- `PostRepositoryPort`와 `PostRepositoryAdapter` 분리로 서비스 계층이 JPA 구현에 직접 묶이지 않는다.
- `PostCreateRequest`의 `@NotBlank`, `@Size`로 서버 입력 검증이 최소 수준 이상 존재한다.
- 정적 화면이 등록, 목록, 상세, 수정으로 나뉘어 CRUD 사용자 흐름이 코드상 완결되어 있다.
- 서비스와 컨트롤러 테스트가 있어 핵심 CRUD 응답 계약 일부는 회귀 확인이 가능하다.

## 6. 구조적 한계
- `auth`와 `global.exception` 패키지는 비어 있어 구조만 있고 기능은 없다.
- `SecurityConfig`는 API를 전부 열고 정적 페이지를 막아 실제 사용 흐름과 충돌한다.
- 서비스 계층은 대부분 저장소 위임만 수행해 도메인 규칙을 담는 층으로 발전하지 못했다.
- 공통 예외 처리와 공통 오류 응답 포맷이 없어 프런트와 백엔드 계약이 약하다.
- 컨트롤러 테스트가 보안 필터를 끄고 실행돼 실제 권한 문제를 발견하지 못한다.
- 저장소 통합 테스트와 프런트 테스트가 없어 H2 매핑과 브라우저 동작은 보호되지 않는다.
- 생성 화면과 수정 화면의 JS 검증 로직이 중복되어 변경 비용이 커진다.

## 7. 유지보수성 관점 총평
아래 4개 항목으로 정리한다.

- 변경 용이성: 게시글 CRUD 범위 안에서는 파일 분리가 되어 있어 수정 위치는 찾기 쉽다. 다만 공통 예외와 공통 UI 로직이 없어 횡단 변경은 여러 파일 수정으로 번질 가능성이 높다.
- 기능 확장 용이성: 포트-어댑터 구조와 계층 분리는 확장 여지를 준다. 하지만 인증, 공통 예외, 공통 보안 규약이 비어 있어 사용자 기능이나 권한 기능을 추가하려면 구조를 먼저 보강해야 한다.
- 버그 발생 가능성: 보안 설정과 정적 UI 접근 경로가 이미 충돌하고 있다. 테스트가 이 런타임 불일치를 막지 못해 회귀 가능성이 남아 있다.
- 리팩토링 필요도: 중간 이상이다. JS 공통화, 예외 응답 표준화, 보안 정책 정리, 통합 테스트 보강이 우선 과제다.
