# AI Prompt Strategy Experiment Report

## 1. 실험 개요

실험 목적  
동일한 기능을 서로 다른 프롬프트 전략으로 개발했을 때 구조, 코드 품질, 테스트, 유지보수성이 어떻게 달라지는지 비교한다.

실험 환경  
- 동일한 초기 저장소 상태
- 동일한 AI 툴
- 동일한 모델
- 시간 제한 20~30분
- H2 Database
- 단순 HTML/CSS/JS 기반 게시판 CRUD

평가 기준  
- 빌드 성공
- 실행 가능
- 테스트 개수
- 테스트 품질
- 패키지 구조
- 권한 처리
- 예외 처리
- 코드 중복

점수 규칙  
- 우수 = 3점
- 보통 = 2점
- 미흡 = 1점
- 확인 불가 = 0점

분석 대상 메모  
요청문에는 `review-*.md`가 언급되었지만, 실제 `demo_코드리뷰_분석` 폴더에는 아래 5개 분석 문서가 존재했다. 본 보고서는 존재하는 5개 문서를 모두 근거로 작성했다.

- `01_bad_prompts_board_service_analysis.md`
- `02_structured_prompts_board_service_analysis.md`
- `03.Role-high_Structured_analysis.md`
- `04_prd_based_prompts_board_service_analysis.md`
- `05_prd_tdd_prompts_board_service_analysis.md`

## 2. 분석 대상 프롬프트 전략

### 2.1 Bad Prompt

파일명 기준 `01_bad_prompts_board_service_analysis.md`에 해당한다. 빠른 CRUD 완성에는 성공했지만 권한과 예외 정책이 프레임워크 기본값과 문자열 비교에 크게 의존하는 전략으로 기록돼 있다.

### 2.2 Structured Prompt

파일명 기준 `02_structured_prompts_board_service_analysis.md`에 해당한다. `domain/application/infrastructure/presentation` 분리와 유스케이스 세분화가 반영된 구조 중심 전략이다.

### 2.3 PRD Prompt

파일명 기준 `04_prd_based_prompts_board_service_analysis.md`에 해당한다. 요구사항 정리와 CRUD 완성도는 확보했지만, 테스트 투자가 거의 없었던 전략이다.

### 2.4 PRD + TDD Prompt

파일명 기준 `05_prd_tdd_prompts_board_service_analysis.md`에 해당한다. 테스트 우선 개발 흔적은 분명하지만, 실제 보안 설정과 테스트 기대값이 어긋나 전체 테스트 기준 빌드 실패가 발생한 전략이다.

### 2.5 추가 관찰: Role-high Structured

`03.Role-high_Structured_analysis.md`는 요청된 4개 핵심 분류 외에 실제 폴더에 추가로 존재한 구조화 변형 케이스다. 구조 요구사항 반영 정도와 실제 완성도 사이의 차이를 보여 주는 보조 비교군으로 포함했다.

## 4. 정성 분석

### 4.1 Bad Prompt 특징

구조  
`post.domain`, `post.application`, `post.infrastructure`, `post.presentation`으로 기본 계층은 존재한다. 다만 게시글 로직이 단일 서비스와 단일 컨트롤러에 집중돼 있어 확장 시 비대화 가능성이 크다.

코드 스타일  
빠르게 동작하는 CRUD를 우선 완성한 흔적이 강하다. 프런트는 HTML별 인라인 CSS/JS 비중이 높고, DTO와 컨트롤러 내부 예외 처리도 중복이 많다.

테스트  
테스트 파일 4개, 테스트 케이스 22개로 양은 적지 않다. 서비스 권한 실패와 일부 404를 검증하지만, Security 실제 필터 동작과 정적 페이지 접근, 저장소 통합은 보호하지 못한다.

문제점  
권한 처리가 `X-Author-Name` 헤더와 문자열 비교에 의존한다. 공통 예외 처리 범위가 좁고, 응답 형식이 엔드포인트마다 달라 유지보수 리스크가 높다.

### 4.2 Structured Prompt 특징

구조  
`domain/application/infrastructure/presentation` 분리와 서비스 세분화가 가장 명확하다. 생성, 목록, 상세, 수정, 삭제 유스케이스가 분리되어 수정 위치를 찾기 쉽다.

코드 스타일  
백엔드 계층은 비교적 읽기 쉽지만, 프론트는 여전히 화면별 인라인 로직 중심이다. DTO와 헤더 처리 코드의 반복도 남아 있다.

테스트  
테스트 파일 8개, 테스트 케이스 23개로 가장 많다. validation 실패, 헤더 누락, 미존재, 권한 실패까지 일부 다루지만 모두 Mock 중심이라 실제 Security 설정 문제는 드러내지 못한다.

문제점  
보안 경계와 실제 화면 흐름이 충돌한다. `/api/posts` 일부만 열리고 나머지 경로는 인증이 필요해, 프론트의 직접 `fetch` 호출과 런타임 동선이 어긋난다.

### 4.3 PRD Prompt 특징

구조  
기본 패키지 분리는 되어 있으나 유스케이스가 매우 얇고 저장소 구현체에 직접 의존한다. 구조는 있지만 구조적 깊이는 제한적이다.

코드 스타일  
요구사항 기반으로 CRUD, 검증, 공통 예외 응답까지 맞춘 흔적은 보인다. 반면 프런트 네 파일에 메시지 처리, JSON 파싱, 오류 분기, 날짜 포맷이 반복돼 중복 부담이 크다.

테스트  
테스트 파일 1개, 테스트 케이스 1개로 가장 약하다. `contextLoads()`만 존재해 기능 회귀 방지 장치로는 사실상 동작하지 않는다.

문제점  
테스트 공백이 가장 크다. 권한 정책도 `/api/**` 전부 허용, 정적 리소스는 인증 요구라는 불균형 상태여서 UI/API 일관성이 약하다.

### 4.4 PRD + TDD Prompt 특징

구조  
계층 분리와 DTO/응답 타입 분리는 일관적이다. 다만 동일한 필드를 가진 요청, 결과, 응답 타입이 여러 개 존재해 구조가 깔끔해 보이면서도 중복이 증가했다.

코드 스타일  
공통 예외 응답 형식은 가장 정돈돼 있다. 프런트는 여전히 4개 HTML에 유사 `fetch`/메시지 처리 로직이 반복된다.

테스트  
테스트 파일 7개, 테스트 케이스 13개로 TDD 흔적이 명확하다. validation 실패와 공통 오류 응답까지 검증하지만, 실제 보안 기본 설정을 반영하지 못해 13개 중 6개가 실패했다.

문제점  
테스트를 많이 썼지만 실행 가능한 제품으로 이어지지 못했다. 테스트가 런타임 보안 제약과 어긋나면서 CI 기준 빌드 실패가 발생한 점이 가장 큰 약점이다.

### 4.5 Role-high Structured 특징

구조  
포트-어댑터 분리까지 포함해 구조 요구 반영 폭은 넓다. 하지만 `auth`, `global.exception`, `global.security` 일부는 `.gitkeep`만 있고 실제 구현이 비어 있다.

코드 스타일  
구조적 의도는 강하지만 구현 밀도는 `post`에 편중돼 있다. JS 공통화와 공통 예외 응답 규약도 비어 있어 실제 코드 완성도는 구조 설계에 비해 낮다.

테스트  
테스트 파일 6개, 테스트 케이스 18개다. 성공/실패 흐름 일부를 다루지만 `@AutoConfigureMockMvc(addFilters = false)`로 보안 필터를 꺼서 실제 런타임 이슈를 잡지 못한다.

문제점  
구조는 가장 야심차지만 공통 영역이 비어 있다. 즉, 설계 프롬프트가 구조 뼈대를 만드는 데는 유효했지만 실제 운영 완성도를 자동으로 보장하지는 않았다.

## 5. 주요 발견 (Key Findings)

1. 구조화된 프롬프트는 총점과 테스트 수를 끌어올렸지만, 보안 설정과 실제 실행 흐름까지 자동으로 정합시키지는 못했다.
2. PRD 프롬프트는 요구사항 반영과 예외 응답 정리는 가능했지만, 테스트가 거의 없으면 결과물 신뢰도는 빠르게 떨어졌다.
3. PRD + TDD 프롬프트는 테스트 수와 오류 응답 설계 측면에서는 분명한 장점이 있었지만, 테스트가 실제 런타임 보안 정책과 어긋나면 오히려 빌드 실패라는 역효과가 발생했다.
4. 모든 전략에서 권한 처리는 `미흡(1점)`으로 수렴했다. 즉, 이번 실험에서는 프롬프트 전략보다 인증/인가 요구사항 명시 여부가 더 결정적이었다.
5. 구조 점수는 전 전략이 모두 `보통(2점)`이었다. 구조를 "만드는 것"은 어느 정도 가능했지만, 공통 예외, 보안, 프런트 공통화까지 채워 넣는 완성도에서는 차이가 났다.
6. 코드 중복은 Bad Prompt와 PRD Prompt에서 특히 두드러졌고, Structured 계열과 PRD+TDD는 상대적으로 완화됐지만 여전히 프런트 중복은 공통적으로 남았다.

## 6. 유지보수성 비교

변경 용이성  
Structured Prompt가 가장 안정적이다. 서비스 분리와 책임 경계가 명확해 수정 위치 추적이 쉽다. 반면 Bad Prompt와 PRD Prompt는 DTO, 헤더 처리, 프런트 스크립트 중복으로 정책 변경 시 파급 범위가 크다.

확장성  
Role-high Structured와 Structured Prompt는 계층 분리 자체는 확장 친화적이다. 다만 공통 보안과 예외 정책이 비어 있거나 얕아서 실제 기능 확장 전 선행 정비가 필요하다. PRD+TDD는 타입이 지나치게 세분화돼 새 기능 추가 시 DTO 증식 부담이 예상된다.

버그 위험  
PRD Prompt는 테스트 공백 때문에 회귀 위험이 가장 크다. PRD+TDD는 테스트가 있음에도 실제 보안과 불일치해 현재 시점의 운영 리스크가 크다. Bad Prompt는 문자열 기반 권한 검증 때문에 보안 우회 위험이 가장 직접적이다.

종합 판단  
이번 실험에서는 "구조화된 프롬프트"가 유지보수성의 출발점을 가장 안정적으로 만들었고, "TDD 프롬프트"는 보안 설정 같은 실행 조건까지 프롬프트에 명시되지 않으면 기대한 만큼의 품질 보증으로 이어지지 않았다.

---

## 7. 실험 한계

1. 분석 근거는 코드 리뷰 문서 5개이며, 각 문서가 이미 요약한 관찰 결과를 재분석한 2차 분석이다.
2. 실험 시간 제한이 20~30분이어서 장기 리팩토링이나 운영 환경 검증까지 포함하지 못했다.
3. 단일 게시판 CRUD 프로젝트이므로 다른 도메인이나 대규모 시스템에 바로 일반화하기는 어렵다.
4. 동일 모델과 동일 툴 조건이라도 프롬프트 외 미세한 상호작용 차이가 결과에 영향을 줄 수 있다.
5. `Role-high Structured`는 요청된 4대 분류 외 추가로 존재한 사례이므로, 핵심 비교군과 보조 비교군을 완전히 동일 선상으로 해석할 때는 주의가 필요하다.

## 8. 결론

이번 실험에서 가장 높은 총점은 Structured Prompt(16점)였다. 구조화된 프롬프트는 유스케이스 분리, 테스트 수, 예외 처리 일관성에서 상대적으로 안정적인 결과를 만들었다.

반면 PRD Prompt는 요구사항 반영은 되었지만 테스트 부족으로 품질 보증이 약했고, PRD + TDD Prompt는 테스트를 많이 썼음에도 보안 설정과 맞물리지 못해 전체 테스트 기준 빌드 실패가 발생했다. 즉, 프롬프트 전략은 분명 결과물에 영향을 주지만, 특히 권한 정책과 실행 조건을 얼마나 명시적으로 요구하느냐가 구조 품질과 테스트 품질을 좌우하는 핵심 변수로 확인됐다.
