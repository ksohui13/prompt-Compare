# 프롬프트 전략 비교 요약 (발표용)

## 1) 한 장 요약 (Executive Summary)

- 동일한 CRUD 기능 구현에서 **프롬프트 구조화 수준**이 결과 품질 차이를 만들었다.
- 세 전략 중 종합 점수는 **Structured(16) > Bad(14) > PRD(13)** 순이었다.
- 차이를 만든 핵심 변수는 `구조화된 지시`, `테스트 요구 강도`, `권한/보안 요구 명시 여부`였다.
- 특히 권한 처리는 세 전략 모두 낮았고(모두 미흡), 테스트 투자가 부족하면(PRD) 빠르게 신뢰도가 하락했다.

## 3) 프롬프트 입력 설계 차이

| 구분 | Bad Prompt | Structured Prompt | PRD Prompt |
|---|---|---|---|
| 지시 방식 | 짧고 모호한 요청 | endpoint/scope/output 형식 명시 | PRD 해석 후 구현 지시 |
| 출력 통제 | 약함 | 강함(Plan/Reasoning/Implementation 등) | 중간~강함(PRD 기준 준수) |
| 기능 분해 | 단계는 있으나 제약 약함 | 기능 단위 + API 단위 명확 | PRD 기반 시나리오 중심 |
| 테스트 요구 | 최소 수준 | JUnit 명시 | 테스트 직접 요구 약함 |
| 리스크 | AI 자율 판단 과다 | 형식 준수 편향 가능 | 문서 해석 편차/누락 리스크 |

핵심 해석
- Bad는 자유도가 높아 빠르지만 품질 편차가 크다.
- Structured는 실행 가능성과 일관성을 가장 안정적으로 확보했다.
- PRD는 요구사항 정합성은 높지만 테스트 장치가 약하면 품질 보증이 급격히 떨어진다.

## 5) 정성 비교 포인트

### A. 구조/유지보수성
- Structured: 유스케이스 분리와 책임 경계가 가장 명확.
- Bad: 계층은 있으나 서비스/컨트롤러 집중도가 높고 확장 시 비대화 가능성 큼.
- PRD: 패키지 분리는 있으나 유스케이스 깊이가 얕고 중복 관리가 약함.

### B. 테스트
- Structured/Bad: 단위+컨트롤러 테스트가 의미 있게 존재.
- PRD: `contextLoads()` 1건 중심으로 회귀 방어력이 매우 낮음.

### C. 보안/권한
- 세 전략 모두 공통 약점.
- 인증/인가를 제품 정책 수준으로 강제하지 않으면, 헤더/클라이언트 값 의존 등 우회 가능한 구현으로 수렴.

### D. 예외/응답 일관성
- Structured, PRD가 Bad 대비 공통 예외 처리 측면에서 상대적으로 나음.
- 다만 보안 예외/런타임 예외까지 완전 통일되지는 않음.

### E. 코드 중복
- Bad/PRD에서 DTO·프론트 JS 중복이 더 크게 관찰.
- Structured는 상대적으로 완화됐지만 프론트 공통화는 여전히 부족.

## 6) 발표용 핵심 메시지 (권장 문구)

1. "프롬프트를 구조화하면 구현 품질이 자동으로 완벽해지지는 않지만, **일관성 있는 기본 품질**은 확실히 올라간다."
2. "PRD 기반 접근은 요구사항 정합성에 강하지만, **테스트 요구를 함께 강제하지 않으면** 품질 보증이 약해진다."
3. "이번 실험에서 가장 큰 병목은 프롬프트 유형이 아니라 **권한/보안 요구의 명시 부족**이었다."

## 7) PPT 장표 구성안 (8장)

### 슬라이드 1. 실험 목적
- 동일 기능 + 다른 프롬프트 전략 비교
- 비교 축: 구조/테스트/권한/예외/중복

### 슬라이드 2. 비교 대상
- Bad vs Structured vs PRD
- 각 전략의 지시 방식 1줄 정의

### 슬라이드 3. 프롬프트 설계 차이
- 표: 지시 강도, 출력 통제, 테스트 요구, 리스크

### 슬라이드 4. 정량 결과
- 총점 바차트: Structured 16, Bad 14, PRD 13
- 테스트 수 보조 지표 함께 표시

### 슬라이드 5. 품질 차이의 원인
- Structured: 유스케이스 분리 + 명확한 제약
- PRD: 테스트 공백
- Bad: 모호한 지시로 편차 확대

### 슬라이드 6. 공통 취약점
- 권한/보안 미흡(세 전략 공통)
- 프론트 중복/응답 일관성 문제

### 슬라이드 7. 실무 적용 가이드
- PRD + Structured + 테스트/보안 체크리스트 결합 제안
- "요구사항 명시"와 "검증 명시"를 분리해 강제

### 슬라이드 8. 결론
- 추천 기본 전략: Structured 기반 + PRD 입력 + 보안/테스트 강제 항목
- 기대효과: 품질 편차 감소, 유지보수성 개선, 리뷰 비용 절감

## 8) 다음 실험 제안 (사내 확장용)

- 보안 요구를 프롬프트에 강제: 인증 방식, 인가 정책, 실패 시 응답 형식
- 테스트 요구를 수치로 강제: "핵심 유스케이스 N개 + 실패 시나리오 N개"
- 프론트 공통화 요구 추가: API 클라이언트/에러 핸들러/검증 유틸 공용화
- 결과 산출물 경로 검증 자동화: 프롬프트 내 파일 경로 오타 방지 체크
